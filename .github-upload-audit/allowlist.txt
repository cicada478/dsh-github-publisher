# 敏感信息扫描豁免清单 —— **宿主项目自己的**豁免
#
# 当前状态：**7 条生效条目**（全部为 `tests/selftest.py` 的伪造样本）。
#
# 为什么是空的
# ------------
# 本仓库里那些"看起来像密钥"的字符串，全部位于 **skill 自身的文件**里
# （规则定义与自测夹具）。它们由 skill 自带的
# `.dsh/skills/github-project-publisher/skill-allowlist.txt` 豁免——
# 那是 skill 的自我担保，随 skill 一起分发，见该文件头部的说明。
#
# 本仓库**没有属于它自己的**豁免对象，所以这里是空的。这是正确状态：
# 一个项目的豁免清单应当只登记「这个项目自己的、确实不是敏感信息的命中」。
#
# 加条目的判据——必须同时满足
# --------------------------
#   a. 该命中**确实不是**敏感信息，而不是「我希望它不是」
#   b. 无法用公认占位形式（example.com / your_ / <...> / xxxx 等）消除
#   c. 能写出一句经得起 review 的理由
#
#   不满足任何一条时，正确的做法是**改文档**（把真实值换成占位形式），
#   而不是在这里加豁免。豁免是逃生口，不是常规手段。
#
# 格式
# ----
#   <规则ID>  <路径通配>  <行号|*>  -- <理由>
#
#   理由为必填，且必须由该条目自身给出：行内 `--` 之后，
#   或紧邻上方以 `# reason:` 开头的注释行。
#   **普通的 `#` 注释不构成理由**——否则文件头注释迟早会被当作理由，
#   「理由必填」这条约束就会形同虚设。
#
#   无理由或格式错误的条目会被**拒绝**，并作为问题报告出来。
#   每一条生效的豁免都会写入审计报告，含规则、路径、行号、来源与理由原文。
#
# 两份清单
# --------
#   本文件（宿主项目自己的豁免）+ skill 目录内的 `skill-allowlist.txt`
#   （skill 自身文件的豁免，随 skill 分发）。两份格式与"理由必填"要求完全相同，
#   报告中会标明每条来自哪一份。
#
#   为什么要分两份：skill 会被项目级安装进各种仓库。若 skill 自身文件的豁免也要
#   由宿主项目来写，那么每个安装它的仓库都会收到一批误报，而它并没有立场替
#   别人的文件担保。实测缺少这一份时宿主项目会收到 57 条 BLOCKER 误报。
#
# 依据：references/checks.md 第 4 节
