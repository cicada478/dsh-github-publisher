# 交互与决策分级

本文件定义：**哪些事必须问、哪些事要二次确认、哪些事默认执行、哪些事绝不做。**

规则编号与检查项见 [`checks.md`](checks.md)。

---

## 1. 为什么必须分级

交互设计有两种对称的失败模式，而它们常被混为一谈：

**问得太多。** 如果一个每次运行都必须做的事情（例如生成 SHA256 校验和）也拿来提问，用户很快会形成"无脑确认"的习惯。到真正需要判断的那一次——例如"是否要把仓库公开"——提问已经失去筛选作用。**每一个多余的问题，都在稀释每个必要问题的效力。**

**问得太少。** 如果不可逆的决定被默默做掉（例如默认公开仓库、默认选了许可证），用户在发现时已经无法挽回。

因此本 skill 不采用"该问就问"的模糊标准，而是把每个决策点**预先归入四类之一**，并规定每类的固定处理方式。

---

## 2. 四类决策

| 类别 | 标记 | 处理方式 | 判断标准 |
|---|---|---|---|
| **必须问** | 🟦 | 选项对话卡，带描述与推荐 | 不可逆，或取决于用户意图而无法推断 |
| **二次确认** | 🟧 | 需针对**该具体事项**的明确"是" | 破坏性，或放宽了安全限制 |
| **默认执行 + 留痕** | 🟩 | 不提问，直接执行，记入审计报告 | 无条件该做的事 |
| **红线** | 🔴 | 无明确指令时拒绝执行 | 后果不可逆且风险极高 |

---

## 3. 完整分级表

### 3.1 🟦 必须问（选项对话卡）

| 决策点 | 推荐值 | 推荐理由 |
|---|---|---|
| 仓库名 | — | 无法推断；公开标识，改名会破坏已有链接 |
| 目标账户 / 组织 | 当前已登录账号 | 推错位置代价高 |
| 仓库可见性（初始） | **private** | 私有仓库是敏感信息泄露的第三层缓冲 |
| 许可证 | MIT（工具类项目） | 取决于作者意图，不能代为选择 |
| 文案语言 | 中英双语 | 受众决定 |
| 仓库描述与 topics | 自动生成草稿 | 可改，不必从零询问 |
| 版本号 | 由提交历史推导 | 已有客观依据，但仍需确认 |

**选项卡的设计要求**（这是"必须问"类能否成立的关键）：

1. **每个选项必须带一句描述**，说明选择它的后果或取舍。只有标签没有描述的选项，等于把判断责任推回给用户。
2. **必须标注推荐项并给出理由**。推荐项排在最前，标签末尾标注"（推荐）"。
3. **选项数量控制在 6 个以内**。超出时应先缩小问题范围。
4. 需要用户提供自由文本时，提供一个"我自己定"选项，而不是强迫其在预设中选择。
5. 允许多选时明确标注，避免用户误以为只能选一个。

### 3.2 🟧 二次确认

针对**该具体事项**的明确同意，不接受"继续吧"这类笼统答复。

| 事项 | 确认时必须说明 |
|---|---|
| 改写 git 历史 | 会改变哪些提交的 SHA；若已推送，需强推，且**已公开的内容无法收回** |
| `force push` | 会覆盖远程的哪些提交；是否有其他协作者 |
| 仓库转为公开 | 即将公开的完整内容清单；此操作**不可逆**（可再次转私有，但内容已被抓取） |
| 豁免 `BLOCKER` | 命中内容、位置、风险，以及用户要求豁免的**书面理由** |
| 删除远程分支 / 标签 / 仓库 | 具体对象与影响范围 |
| `git rm --cached` 已跟踪文件 | 文件将从版本控制移除但保留在本地；若已在历史中，需另行处理 |

### 3.3 🟩 默认执行 + 留痕

**不提问。** 每项执行后必须在审计报告中留下记录。

| 事项 | 留痕方式 |
|---|---|
| 敏感信息扫描（四个扫描面） | 报告中记录扫描面、引擎、命中数 |
| SHA256 校验和生成 | 报告中记录文件清单与校验和文件名 |
| 补全 `.gitignore` | 记录新增的规则与依据模板 |
| 补全 `.gitattributes` | 记录新增的规则 |
| 设置本地 noreply 身份 | 记录"仅修改 local，未改动 global" |
| 生成 CHANGELOG 初版 | 记录来源提交范围 |
| 新建仓库设为 private | 记录创建后的可见性复核结果 |
| 上传后远程复核 | 记录复核项与结果 |
| 生成审计报告 | 报告本身即记录 |

> **反例**："要不要帮你生成校验和？"——这是典型的问错对象。校验和是发布物完整性的前提，不是可选项。每次都问，只会训练出无脑确认。

### 3.4 🔴 红线

无**明确指令**时一律拒绝执行，且不主动提议。

| 事项 | 理由 |
|---|---|
| 将仓库公开 | 内容一旦公开即被爬取、缓存、归档，不可收回 |
| `force push` 到已有远程 | 可能覆盖他人提交，不可恢复 |
| 删除远程仓库 / 分支 / 标签 | 破坏性且影响他人 |
| 修改**全局** git 配置 | 影响用户机器上所有其他仓库 |
| 回显密钥或邮箱原文 | 使报告、终端、会话记录成为新的泄露源（CWE-532） |
| 绕过 `BLOCKER` 直接提交 | 使硬阻断机制失效 |
| 未完成人工核验即发布 Release | 发布物对全网可见 |

## 4. 提问的反模式

以下做法在本 skill 中被明确禁止：

| 反模式 | 问题 |
|---|---|
| 用是非题问本该给选项的决策 | "用 MIT 吗？"使替代方案不可见，用户只能接受或拒绝 |
| 选项没有描述 | 把判断成本转回用户，等于没问 |
| 没有推荐项 | 用户需要自行评估全部利弊，而 agent 本已掌握上下文 |
| 把默认执行项拿来提问 | 稀释真正需要判断的问题 |
| 一次抛出十几个问题 | 用户会跳过，实际决策质量低于逐项询问 |
| 用模糊措辞取得"同意" | "我继续处理了"不构成对 force push 的授权 |
| 替用户决定许可证 | 许可证是法律声明，不是技术选择 |

## 5. 豁免协议

当用户要求放行一个 `BLOCKER` 时：

1. 说明**具体命中了什么**（规则 ID、文件、行号），以及**不回显原文**的掩码
2. 说明**不处理的后果**：若已推送过，须明确告知"改写历史不能收回，唯一彻底的处理是轮换凭据"
3. 要求给出**理由**
4. 将豁免写入 `.github-upload-audit/allowlist.txt`，格式与理由要求见 [`checks.md`](checks.md)
5. 在审计报告中记录该豁免

**无理由的豁免不予受理。** 这不是形式主义：豁免记录是事后判断"当时是否知情"的唯一依据。

## 6. 特定检查项的选项卡

### 6.1 `GIT-004`：历史中的大文件

#### 先讲清楚 `.gitignore` 管什么

这决定了下面哪些选项才成立：

| 动作 | 对**当前版本** | 对**历史里的副本** | 对**项目体积** |
|---|---|---|---|
| 把文件删掉 | 移除 | 无影响 | **无影响** |
| 写进 `.gitignore` | 无影响（文件已不在） | 无影响 | **无影响** |
| `git rm --cached` | 停止跟踪 | 无影响 | **无影响** |
| **改写历史** | 按操作而定 | **移除** | **变小** |

**一句话：`.gitignore` 只能阻止未来的提交，永远清除不了历史。**

所以它**只在"文件还在当前版本里"时才有意义**——用来防止你或别人把它再提交一次。它**不会**让体积变小，**不会**让 GitHub 不再拒收。

#### 判据：先看发现项怎么写的

`GIT-004` 的消息会明确区分两种情况，选项必须跟着变：

- 「该路径**当前仍被跟踪**」→ 用情况 A
- 「该路径在当前版本中**已不存在**，只留在历史里」→ 用情况 B

**情况 B 里不得提供"写进 `.gitignore`"这个选项**——没有可忽略的对象，给了就是误导。

#### 情况 A：文件仍在当前版本里

| 选项 | 描述 |
|---|---|
| **改写历史，彻底移除**（若尚未推送，推荐） | 用 `git filter-repo` 把它从**所有历史提交**中删除。这是**唯一能让项目真正变小**的办法。代价：所有相关提交的编号（SHA）都会改变；若已推送则需强推，且别人已下载的副本不受影响 |
| **从当前版本移除并写进 `.gitignore`** | 执行 `git rm --cached <文件>` 并把路径写进 `.gitignore`。**只阻止将来再被提交**；⚠️ **历史里那份原封不动，体积不会变小，GitHub 该拒收还是拒收。** 它应当与"改写历史"配合使用，而不是替代它 |
| **改用 Git LFS 托管** | 把大文件迁到 Git LFS。适合"这个文件确实需要留在项目里"（设计稿、模型权重、测试数据）。代价：需要 LFS 配额；使用者下载时依赖 LFS；历史里的旧副本仍需改写才能清除 |
| **什么都不做，接受现状** | 仅当体积在 **50–100 MB** 之间时可选：推送会成功，只是有警告。代价：**项目体积永久变大**，每个下载的人都得拉下来。超过 100 MB 时此选项不存在——GitHub 会直接拒绝 |

#### 情况 B：文件只在历史里

| 选项 | 描述 |
|---|---|
| **改写历史，彻底移除**（推荐） | 同上。此时它是唯一直接有效的办法 |
| **改用 Git LFS 托管** | 若该文件**仍然需要**留在项目里（例如它被误删了），先用 LFS 把它重新纳入，再清理历史里的旧副本 |
| **什么都不做，接受现状** | 仅当体积在 50–100 MB 之间。超过 100 MB 时无法推送 |
| **弃用当前仓库，另开一个干净的** | 当历史已经被污染得难以清理时，重来往往比修更干净。适合项目早期、提交历史价值不大的情况。代价：**丢失全部提交历史** |

#### 提问时必须说清的几句话

无论用哪张卡，都要在描述里明确：

1. `.gitignore` **不清除历史**，也不减小体积
2. 改写历史会**改变提交编号**
3. 若已推送到公开仓库，改写**无法收回**别人已经下载的副本
4. 超过 100 MB 时，"什么都不做"不是可选项

## English summary

Two symmetric failure modes drive this design. Asking too much — putting mandatory actions such as SHA256 checksum generation to a vote — trains the user to confirm without reading, which destroys the value of the questions that genuinely matter. Asking too little lets irreversible decisions happen silently.

Every decision point is therefore pre-assigned to one of four classes: **Ask** (irreversible or intent-dependent — presented as an option card where every option carries a description and one is marked as recommended with a reason); **Confirm** (destructive or safety-loosening — requires an explicit yes for that specific item, not a general "go ahead"); **Default and log** (unconditional — executed without asking, recorded in the audit report); and **Never** (refused absent an explicit instruction, never volunteered).

Waiving a BLOCKER requires a written reason and is recorded. An exemption without a justification is not accepted, because the record is the only evidence of what was known at the time.
